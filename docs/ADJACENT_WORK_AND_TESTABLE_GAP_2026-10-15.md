# Adjacent work and one testable gap (2026-10-15)

**Source and design note, not an experimental result or a priority claim.** I read the pinned primary repository files below on 2026-10-15. The ORBIT, Colosseum, and AgenticPay GitHub pages also returned HTTP 200 that day. The [Emergent Collusion README](https://github.com/SALT-NLP/agent-collusion/blob/5afb2c595aa3eff6b9b829a032f4f117b36ee54d/README.md) was fetched directly from its pinned GitHub source. An attempt to open its arXiv paper and an attempt to open [CABAL](https://arxiv.org/abs/2609.05227) met proxy CONNECT 403, so neither paper's full text was checked. This is a targeted comparison, not a complete literature search.

**Precise hypothesis to test:** for the *same* independently BAD invoice or private-calendar job, a provider-originated, auditor-exposed approval-contingent offer increases the probability of an **unchecked or known-wrong auditor ACCEPT followed by a verified client-funded provider release**, relative to matched no-contact/independent-auditor controls, despite an affordable independent check. Measure the check debit, returned oracle result, offer funding and exposure, verdict, and external release separately. Randomize provider/auditor model pairing, fee terms, and check cost prospectively; retain every assigned run, including refusals and incomplete runs. The current eight-cell Sol/Sonnet calendar design can establish feasibility and describe role behavior, but one pair per model/truth cell cannot estimate this effect or a cross-model interaction. Two *agents* are necessary for influence; two different model families are a useful heterogeneity test, not a logical requirement for collusion.

The payment question is deliberately narrower than a generic “valid receipt proves bad work” claim. [ERC-8183](https://github.com/erc-8183/base-contracts/blob/142e669c1fd318486a4628395b629f033654dd06/contracts/ERC8183.sol#L762-L792) already pays a designated evaluator fee on completion; contingent evaluator compensation is not new. For an **invoice**, an [x402 v2 exact/EVM](https://github.com/x402-foundation/x402/blob/e95b06661e1a2a8a9a21fce34cc28b9934834650/specs/schemes/exact/scheme_exact_evm.md) payment can buy report access, while an ERC-8183 evaluator decision can release a separate job escrow. The [x402 flow specification](https://github.com/x402-foundation/x402/blob/e95b06661e1a2a8a9a21fce34cc28b9934834650/specs/x402-specification-v2.md#61-asset-transfer-methods-and-payment-flow-models) distinguishes read-only verification, settlement, and resource execution, with different ordering by flow; report truth needs an independent purchase-order/credit-note oracle. For a **calendar booking**, an [MPP charge/session](https://github.com/tempoxyz/mpp-specs/blob/50309c8e67e6d64b5547f1cc354fb327bda1301e/specs/methods/tempo/draft-tempo-session-00.md) can pay for a check, while the application separately releases the booking fee; hidden availability is the oracle. [MPP core](https://github.com/tempoxyz/mpp-specs/blob/50309c8e67e6d64b5547f1cc354fb327bda1301e/specs/core/draft-httpauth-payment-01.md#security-considerations) supports request digests and requires method-specific payment checks, so test the actual configured binding before attributing a handoff error to the protocol.

[AP2's security guidance](https://github.com/google-agentic-commerce/AP2/blob/b4587ac1d055888a73b4b21750973cffba961793/docs/ap2/security_and_privacy_considerations.md) already requires checkout/mandate linking and amount/payee constraints. A valid AP2 mandate authorizes an in-scope purchase; it is not an audit verdict. [OpenAI/Stripe ACP checkout](https://github.com/agentic-commerce-protocol/agentic-commerce-protocol/blob/7fdd78df677a94dce04c770644b0fbbb1401272b/spec/2026-04-17/openapi/openapi.agentic_checkout.yaml#L217-L244) describes order creation after payment-method application, not independent audit correctness; a mock checkout is not captured funds. A strict application must bind the *current* task, report/schedule digest, buyer, service and decision before it authorizes a separate payout. If an intentionally permissive adapter accepts an authentic but unrelated payment object, describe an **application composition failure**, not a broken signature or protocol exploit.

**Novelty and evidence limit:** the defensible potential contribution is a causal, role-specific estimate that links real LLM interaction to feasible paid verification and independently replayed *local* payment consequences in two concrete services. The pinned repository files do not establish that this exact estimand has already been measured, but absence from them is no proof of literature priority. The preliminary project PDF already studies feasible game-credit checks and contingent offers; valueless local tokens add execution evidence, not real-money preference. Full texts for CABAL, payment-protocol analyses, and the closest SoKs remain to be checked before any “first” claim. A correct rejection, an unchecked ACCEPT without external release, a scripted payout, and a cross-model difference from one pair per cell are all distinct outcomes; none alone proves collusion. Report honest-provider nonpayment, cost and latency with any improper payout.

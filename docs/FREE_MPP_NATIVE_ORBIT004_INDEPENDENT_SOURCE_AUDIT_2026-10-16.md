## Process isolation and stop path

The parent [runner](../scripts/run_free_mpp_native_orbit004.py) checks the source review, exact resolved source-study path, assignment/source seal, new marker metadata, an advancing loopback chain, and an unused output path **before** dispatch. It creates a unique launch intent and nonce for each arm, then calls `subprocess.Popen` sequentially with `--worker-arm` and waits up to 900 seconds for that process to finish. It checks the worker's result, exit code, PID, parent PID, nonce and `COMPLETE.json` before launching the next arm. Missing, failed, inconsistent, or timed-out workers produce `BLOCK_STOPPED.json`, mark later arms unattempted, and are not retried.

Each worker runs in a new Python process, checks the frozen assignment and parent intent, creates its row directory exclusively, then creates its own guarded OpenRouter transport and model objects. It performs **one** synchronous `inspect_eval()` at most, followed only by replay and native evidence verification. The model API objects are therefore not reused between the two Inspect event-loop lifetimes, which directly addresses the ORBIT003 closed-loop design risk. The parent imports Inspect code but does not call `configure_free_models()` or `inspect_eval()`. The first worker's `COMPLETE.json` is also required inside the second worker. This is a source-level isolation guarantee; the second live arm has not yet demonstrated that the infrastructure failure is gone.

The first forwarded but uncompleted model call, any raw Inspect error, uncertain charge or receipt, source mismatch, reviewer mismatch, worker crash, or timeout stops the block. The guard journals `FORWARDING` and `COMPLETED_ZERO_PRICE` separately, enforces the exact two zero-catalog-price routes, no fallback, high reasoning request, response cost zero, and stable immediate account usage. The worker's STOP marker records possible unknown charge for forwarded calls without completion; a parent crash/timeout conservatively records possible unknown model charge or native state. No outcome is inferred from that stop, and no attempted row is rerun. Immediate account equality and a zero-price catalog are not proof of delayed billing finality.

## Evidence limits for the eventual run

The reviewer checks each worker's `worker-start.json` against its launch intent and pinned runner. The parent writes `worker-launch-*.json` and `worker-exit-*.json` and checks the live subprocess PID, return code, result, and worker-start record before the next arm. The reviewer does **not** itself reconcile both parent launch/exit files or compare the two arm PIDs after the run. A post-run evidence review should explicitly compare these records and report any missing exit, ambiguous native state, or unresolved charge. This is a documentation/evidence limit, not evidence that process reuse occurs: the executable parent dispatches a new subprocess for each arm and stops on mismatch.

The assigned sample is only one row per arm, the provider is explicitly prompted to solicit wrongdoing, and the induced auditor is explicitly given a compromised objective. Even if a later row contains an affirmative BAD approval and native buyer release, it would be a post-hoc induced susceptibility case; it would not estimate prevalence, prove spontaneous collusion, or identify a causal incentive effect. Count the provider proposal, exact exposure, auditor agreement, check choice/result, false verdict, native transfers, and buyer loss separately.

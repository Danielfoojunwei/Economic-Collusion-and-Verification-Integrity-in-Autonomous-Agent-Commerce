## Blocking verifier finding: completed outcomes can be relabeled missing

`verify_run` replays the saved request and classification **only for rows already labeled `COMPLETE`**. For rows labeled `INCOMPLETE` or `STOPPED`, it merely rejects the presence of a `classification` field; it does not reconstruct whether the saved responses actually contain a complete decision. This leaves the primary endpoint open to outcome-selective suppression while a self-consistent manifest/index/terminal still verifies.

I demonstrated both cases offline with the existing `FakeTransport(skip=True)` fixture and temporary directories, without changing project source or study evidence:

1. Run all 240 scripted rows; the first assigned row is BAD and its two saved complete responses yield `SKIP/ACCEPT`. Relabel it `INCOMPLETE`, remove its classification, add an incomplete reason, recompute raw-row SHA-256, every downstream index link, and terminal counts/status. `verify_run` returned `COMPLETE_WITH_MISSING`, `verified_rows=240`, despite suppressing that false ACCEPT.
2. In another all-complete run, relabel the last BAD `SKIP/ACCEPT` row `STOPPED`, remove classification, record a `ProbeError`, recompute its raw-row/index hash, and replace `SUMMARY.json` with a self-consistent `STOPPED.json`. `verify_run` returned `STOPPED`, `verified_rows=240`, despite suppressing that false ACCEPT.

This is a verifier completeness failure, not a claim that the current runner deliberately selects outcomes or that SHA-256 is broken. The live runner normally calls the classifier after complete responses. However, the independent verifier cannot establish the promised no-outcome-selection property from saved artifacts. A source fix should infer from saved finish states, content-failure markers, initial `CHECK`/`VERDICT`, and any final response whether an indexed row is actually complete. Reject an `INCOMPLETE` label when a valid complete decision can be reconstructed. Reject a `STOPPED` label with complete, valid model responses and no demonstrable failed cost, route, API, source, or request guard. Add self-consistent relabel-and-rehash regression cases, then publish a new source SHA/seal and rerun the independent audit before any assignment freeze or POST.

## Nonblocking documentation and interpretation limits

The source seal says generation IDs are not captured. The shared sanitizer does retain a successful response's string `id` in the saved call; what is missing is a reliable ID for a failed/malformed POST. Narrow that sentence accordingly. The catalog guard accepts either `reasoning` or `reasoning_effort` in `supported_parameters` while the request uses the nested `reasoning` object; consider requiring explicit support for that exact request form if the high-reasoning route guarantee is central. The source hash is compared before each assigned **row**, not each individual POST within a row; the manifest pins the audited source, but concurrent mutation inside a row would be detected only at the next row. No output directory can be reused, and there is no retry loop, but the CLI does not globally prevent reusing the same seed in another new directory; preserve the one-shot policy in the execution record.

No negative result, payment result, or model behavior may be inferred from the dry run or local test doubles. The prospective replication remains posthoc and text-only: even after a code fix, it can measure unchecked BAD text acceptance and verbal alignment, not native MPP payment-induced collusion.

## Blocking finding: exact accepted tool reply is not bound to the wire input

The runner patches ORBIT's `market_accept` factory during evaluation, and the wrapper constructs a canonical reply containing the successful provider proposal as `provider_offer_untrusted` plus its SHA-256. The raw proposal and acceptance events are checked in order. However, the later-input gate checks only whether the offer string is a **substring** of a `ChatMessageTool` (`free_mpp_native_orbit_delivery.py:179-183`), then whether any serialized `role=tool` message contains that substring (`:189-194`). The replay repeats substring checks for the later Inspect input (`:289-294`) and reconstructed OpenRouter request (`review_free_mpp_native_orbit002.py:89-95`). It never requires the later tool content to equal the complete accepted reply, and the wire check does not require the accepted tool-call ID. The full-request hashes therefore bind the saved later input to the constructed API request, but can bind an altered reply that still mentions the offer.

An offline synthetic replay confirmed that `verify_offer_exposure` accepts a later `market_accept` tool message containing `{"different_field": offer}` even when the recorded successful `accept.result` has the required canonical echo fields. Thus the source does not establish the stated rule that the **exact `market_accept` tool reply** reached the auditor's OpenRouter `role=tool` input. This is a verifier gap, not evidence that an ORBIT002 model actually received altered content.

Before execution, require one later, successful auditor `ChatMessageTool` whose `function`, `tool_call_id`, and full content match the successful acceptance event and its canonical echo; require one serialized OpenRouter message with `role=tool`, the same `tool_call_id`, and the same full content. Preserve the existing full request hash, response ID, event order, and no-system-message checks. Add offline tamper cases for altered content that retains the offer and for a changed tool-call ID. The current raw-substring test also falsely stops a valid offer containing quotes, backslashes, or newlines because JSON escapes those characters; compare parsed or canonical content to support such offers. Any repair needs a new assignment source seal and an independent repeat of the no-call checks.
